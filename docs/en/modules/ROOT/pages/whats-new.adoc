= What's new
:description: Everything that changed in this component since the {release-version} release.

[.lead]
New in the `{project-version}` development line — everything listed here landed **after the {release-version} release** and is not part of it. Every entry links to the section that documents it, and those sections carry the [.tag-new]#NEW# badge. Each brick of the suite keeps its own page of this kind; xref:home::whats-new.adoc[the ecosystem index] gathers them. When the next release train ships, this page is frozen with it and restarts empty on the dev line.

* xref:internals.adoc#generated-code[Generated code and reflective fallback] — one table lists what Cassini generates (adapters, route tables, provider and application descriptors), which tool generates it and when, what uses it at run time and what runs when it is missing, followed by when the fallback runs and how to tell which path ran.
* On Vauban, the `@Path` and `@Provider` beans are found from the annotations the deployment's index read in their class files, instead of two reflective reads per bean at startup; a class outside the index is still read by reflection.
* xref:internals.adoc[Internals] — a generated route names its method's parameter types and the class that carries its annotations: Cassini finds the method with one lookup at startup instead of resolving each type by name and scanning annotations. Routes generated by an older processor are resolved as before.
* xref:internals.adoc[Internals] — `cassini-processor` also generates the adapter of the `@BeanParam` classes and sub-resource classes a resource reaches, when they are compiled in the same build: they no longer get one generated at run time on their first request. A sub-resource locator is called through the adapter of its class instead of `Method.invoke`, and a `@BeanParam` parameter is created and filled through its build-time adapter; without one, both keep the reflective path.
* xref:internals.adoc[Internals] — `cassini-processor` generates a `$$CassiniProvider` descriptor for each `@Provider` class: its priority, media types, pre-matching, constraint, name bindings and entity type. Cassini reads it at startup instead of the annotations, and reads the annotations, as before, for a provider without one. A provider in a named module on the boot layer is found through `provides io.vidocq.cassini.spi.gen.ProviderDescriptor with ...`; the Vidocq application layer adds it from `META-INF/services`.
* xref:usage.adoc#_filters_and_interceptors[Filters and interceptors] — a `@PreMatching` filter runs once per request, before routing. Until 0.4.0-RC1 it ran a second time before negotiation, with a fresh `ContainerRequestContext`: a filter that counts, sets a property or activates a scope saw two requests where there was one.
* The request path recomputes less per request, with no API change: the base URI is built once per listener and host, media types are parsed once and shared, provider selection reads what it resolved at registration, routing checks the verb before the template regex and compares literal templates without one, a request entity is read with a buffer of its `Content-Length`, and the JSON provider no longer probes the module path for `jakarta.activation.DataSource` on every `isWriteable` / `isReadable` call.
* xref:internals.adoc#_virtual_threads_and_async[Virtual threads and async] — on Chappe, with a request scope hook such as the Vidocq runtime's, a deployment without Server-Sent Events dispatches each request on the virtual thread of its connection instead of starting one per request. `CassiniHttpAdapter.mayStream()` tells a transport whether it may.
* The arguments of a resource method are resolved from what its parameter annotations say, read once per method instead of on every request, with no API change. The JDK takes a lock on every `Parameter.getAnnotation` and parses the class file again on every `Parameter.getAnnotations()`: a method with a `@PathParam` and an entity paid both on every call.
* xref:internals.adoc[Internals] — a reader, writer or filter whose class declares no `@Context` field gets no adapter: the first JSON request no longer generates one at run time for Cassini's own JSON-B provider, nor for the filters of bricks built without `cassini-processor`, and the `RUNTIME CODE GENERATION FALLBACK` warning no longer names them.
* A resource whose class declares no `@Context`, `@BeanParam` or `@*Param` field skips the field injection on each request and, under CDI, the extra bean resolution that looked up the instance behind the client proxy.
* On Vauban, the bean provider resolves a resource or provider class once instead of on every request: a normal-scoped bean is served by the client proxy the container always hands out for it, a `@Dependent` one is still created on each lookup.
* On Chappe, a request header is looked up by name in Chappe's own headers, and the map of all of them is built at most once per request; it was rebuilt, with a list per name, on each of the half-dozen reads of a request.
* `CassiniHttpExchange.writeResponseBody(byte[])` hands a whole response body to the transport in one call; by default it writes it to `responseBody()`. On Chappe, the exchange keeps the array of an entity written at once instead of copying it into a growing stream and copying that again for Chappe.
* The default scope `CassiniScopeExtension` gives a resource (`@RequestScoped`), a provider (`@Dependent`) or an `Application` subclass (`@ApplicationScoped`) is logged at DEBUG: run at every build of an application, it was an INFO line per class.
* xref:internals.adoc[An adapter generated at run time is announced] — when a resource or provider adapter is generated at run time instead of by `cassini-processor` at build time, Cassini logs a framed `CASSINI — RUNTIME CODE GENERATION FALLBACK` warning naming the classes, at start-up or on first use. A build-time adapter is recognised by its class file, without loading it; the Maven plugin writes its own adapters again on every run; no `newInstance()` is generated for an abstract or inner resource.
* *Jakarta REST conformance fixes* — the multipart part name is read when `filename` comes first (CASSINI-026); `EntityPart.Builder` follows its contract (CASSINI-027); the stack's `Application` is exposed to its requests (CASSINI-028); `UriInfo` keeps `+` in paths and parses matrix parameters (CASSINI-029), and `relativize` and the filter view work (CASSINI-031); `SseBroadcaster` follows its close contract (CASSINI-030); each adapter's method ids are read from the adapter itself (CASSINI-032); one §3.6 rule for every way routes are built; `UriBuilder` keeps URI templates in query and matrix parameters, takes positional values in URI order, percent-encodes supplementary characters as one UTF-8 sequence and leads a relative path with a slash after the authority; `ResponseBuilder.status(int, String)` reports its reason phrase; a wildcard locale answers a request without `Accept-Language`; response filters see a non-null status and delegate-converted header strings; `VariantListBuilder` resets after `build()`; a streamed response whose queue is full ends on Chappe.
* *Client fixes* — typed invocations throw `WebApplicationException` on error statuses; async failures are unwrapped and invocation callbacks typed; `readEntity` follows its contract on closed and unreadable responses; response header names are looked up case-insensitively; request properties are scoped to the request and null ones removed; the default `Jsonb` is created on the first JSON entity only.
