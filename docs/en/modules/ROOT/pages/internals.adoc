= Internals
:description: Request sequence diagram, static codegen, Champollion / Vauban integration.

[.lead]
This page describes how an HTTP request flows through Cassini, the codegen-side implementation choices, and the integrations with xref:champollion::index.adoc[Champollion] (JSON) and xref:vauban::index.adoc[Vauban] (CDI). Source of truth: `cassini-core/src/main/java/io/vidocq/cassini/internal`.

[#generated-code]
== Generated code and reflective fallback

Every brick of the suite documents, in a section of this name, what it generates, who generates it and when, what
looks it up at run time, and what runs instead when it is missing. Cassini generates the dispatch of each resource
and the description of each provider at build time; the reflective path stays as the fallback, unchanged. The details
are in <<_static_resource_codegen>>.

[cols="2,2,3,3"]
|===
| Generated | By, and when | Used at run time by | Without it

| `<Resource>$$CassiniAdapter`, a `ResourceAdapter`: direct method calls, `@Context` and `@*Param` field injection,
  parameter coercion
| `cassini-processor` in javac, for every `@Path` and `@Provider` class and the classes they reach (`@BeanParam`,
  sub-resource locators); `cassini-maven-plugin:generate` (`process-classes`) for a dependency jar
| `AdapterRegistry`, when a stack is built or a class is first used: the `ServiceLoader` providers (the module's
  `provides`), then the class's module layer, then `Class.forName(<class>$$CassiniAdapter)`
| Generated at run time with the Class-File API and announced; if that fails too, `Method.invoke` and the
  reflective `FieldInjector`.

| `<Resource>$$CassiniRoutes`, a `RouteProvider`: the route table as literals
| `cassini-processor`
| `RouteRegistry` at startup, the same way: `ServiceLoader`, then by name
| `ResourceScanner` reads the class's annotations once at startup. A class with sub-resource locators is still
  scanned that way.

| `<Provider>$$CassiniProvider`, a `ProviderDescriptor`: priority, media types, name bindings, the type it handles
| `cassini-processor`
| The provider registries (message bodies, exception mappers, filters, context resolvers) when they register a
  provider, through the `ServiceLoader` of its layer or class loader
| The provider's annotations and generic types are read by reflection.

| `<Application>$$CassiniApplication`, an `ApplicationDescriptor`
| `cassini-processor`
| A host that needs the `@ApplicationPath`, through `ServiceLoader`
| The host reads the annotation.
|===

`cassini-processor` also runs in the bricks that ship JAX-RS classes: Grimm, Humboldt, Knock and Cervantes generate
these classes for their own resources and providers at their build.

=== When the fallback runs

* A resource or provider compiled without `cassini-processor` and not processed by the plugin: a jar of another
  build, an instance registered by hand, another container (the generated classes mean nothing to it).
* A resource class with sub-resource locators: its routes come from `ResourceScanner`.
* A closed application module without `opens`, for the run-time generator: it cannot get the private lookup it needs,
  and the request goes through `FieldInjector`.

=== Which path ran

* A framed `WARNING`, _CASSINI — RUNTIME CODE GENERATION FALLBACK_ (logger
  `io.vidocq.cassini.internal.gen.RuntimeGeneration`), lists the resource classes no build-time adapter serves when
  a stack is built; a class generated later gets its own warning, once per JVM.
* `Runtime adapter generation failed for <class> — using reflective fallback` at `WARNING` when even that failed.

== Transport decoupling — golden rule

`cassini-core` contains **no `io.vidocq.chappe` import**. The transport is consumed via `cassini-api` (`CassiniHttpExchange`, `CassiniHttpAdapter`). This is a foundational constraint: a new transport (Netty, Helidon, Vert.x...) can be added without touching the engine.

== Static resource codegen

Rather than reflecting on every dispatch, Cassini generates its artefacts at build time, found at startup through `ServiceLoader` and, failing that, by name (`Class.forName`) — never a classpath annotation scan:

* `<ResourceClass>$$CassiniAdapter` — a `ResourceAdapter` (SPI `cassini-api`, package `io.vidocq.cassini.spi.gen`) that performs **direct method invocation** (no `Method.invoke`), **field injection** of `@Context` / `@*Param`, and **inline `@*Param` coercion**: String/CharSequence, primitives + wrappers, enums (`fromString` or `Enum.valueOf`), public `valueOf`/`fromString`/`(String)`-ctor types, and `List`/`Set`/`SortedSet`/`Collection` of those.
* `<ResourceClass>$$CassiniRoutes` — a `RouteProvider` exposing the route table as string/class literals (`RouteDescriptor`). `RouteRegistry` converts each to a `ResourceMethod` via a targeted `getDeclaredMethod(...)` plus `UriTemplate.compile(...)` — no annotation scan. The descriptor names the parameter types and the class whose declaration carries the method's annotations as class literals, so no type is resolved by name either; a descriptor from an older processor is resolved by name and scanned. Classes carrying sub-resource locators set `hasLocators()` and fall back to `ResourceScanner` for the whole class.
* `<ApplicationClass>$$CassiniApplication`— an `ApplicationDescriptor` for each `Application` subclass with an `@ApplicationPath`: the class and the path as written, listed in `META-INF/services`. A host finds the path through `ServiceLoader`, even when the `Application` is no CDI bean (an unscoped class under `annotated` discovery).
* `<ProviderClass>$$CassiniProvider`— a `ProviderDescriptor` for each `@Provider` class, listed in `META-INF/services`: its `@Priority`, `@Produces`, `@Consumes`, `@PreMatching`, `@ConstrainedTo`, name bindings, and the entity, exception or context type it declares when it is a plain class. Filters, interceptors, readers, writers, exception mappers, context resolvers and param converter providers are registered from it at startup, without reading their annotations. It is found by type through the `ServiceLoader` of the provider's module layer (or of its class loader on the class path), so a provider in a named module on the boot layer needs `provides io.vidocq.cassini.spi.gen.ProviderDescriptor with ...`; the Vidocq application layer adds that from `META-INF/services`. A provider without a descriptor (another container, a class built without the processor, an instance registered by hand) is read by reflection, as before.

=== Three generation tiers

Adapters come from one of three generators, most-preferred first (`AdapterRegistry.lookup`):

. **APT — compile time** (`cassini-processor`): emits `+$$CassiniAdapter+` / `+$$CassiniRoutes+` *source* via `Filer` for every `@Path` / `@Provider` of the current build, and an adapter for each class of the build they reach through a `@BeanParam` field or parameter or a sub-resource locator's declared return type. Plain Java, no bytecode manipulation, AOT-safe.
. **Maven plugin — build time** (`cassini-maven-plugin:generate`, bound to `process-classes`): pre-generates adapters for **external archives** (dependency JARs) by calling `RuntimeAdapterGenerator.toBytecode(cls)` and writing the `.class` files to `target/classes`. AOT-safe.
. **Runtime generator** (`RuntimeAdapterGenerator.generate`, Class-File API / JEP 484): JVM-only fallback when neither of the above produced an adapter.

The runtime generator is the exception, so Cassini announces it with a framed `WARNING` (`CASSINI — RUNTIME CODE GENERATION FALLBACK`, logger `io.vidocq.cassini.internal.gen.RuntimeGeneration`). When a stack is built, one warning lists the resource classes no build-time adapter serves. Each class generated later and not yet named, such as a sub-resource or a bean parameter, gets its own warning on first use. A class is announced once per JVM. The fix the warning gives is to put `cassini-processor` on the annotation processor path of the module that declares the classes, or to run the plugin's `generate` goal on the archive that holds them.

A provider (message body reader or writer, post-matching filter) whose class declares no `@Context` field has nothing to inject, so it gets no adapter at all. This covers Cassini's own JSON-B reader and writer and the filters other bricks ship without running `cassini-processor`. Until 0.4.0-RC1 each of them got an adapter generated on the first request it served.

`AdapterRegistry.lookup` first consults the map of **`ServiceLoader`-registered adapters** (module-path `provides ResourceAdapter with <Class>$$CassiniAdapter` or classpath `META-INF/services`, keyed by `ResourceAdapter.resourceClass()` — the only path that keeps a strict Java Modules resource package closed, with no `opens`/`exports`), then the adapter provided in the module layer of the resource class, which the context class loader of the first scan does not see, then tries `Class.forName(<class>$$CassiniAdapter)` (APT/plugin output), then the runtime generator, then caches a `SENTINEL` so the request falls through to the reflective `FieldInjector` safety net without retrying.

=== Documented residual reflection

Codegen does not erase reflection entirely; the remainder is one-time or structurally irreducible, never on the hot path:

* `ResourceScanner` runs once at startup, only for classes without a generated `$$CassiniRoutes` (i.e. those with locators).
* Resource / bean instantiation (`getDeclaredConstructor().newInstance()`) — one-time per scope; M6a prefers a generated `newInstance()` factory when an accessible no-arg constructor exists.
* The `FieldInjector` filet applies only when codegen *cannot*: a closed application module (no `opens` → `privateLookupIn` fails), or a field whose **type** is a package-private class from another package than the resource (a Java language rule, not a bug).

Benefits: cold start under ~50 ms, **AOT**-compatible (GraalVM `native-image`, Leyden CDS), and predictable.

== Champollion integration (JSON)

`CassiniJsonbReaderWriter` (in `cassini-core/internal`) implements `MessageBodyReader<Object>` + `MessageBodyWriter<Object>` for `application/json` and delegates to the JSON-B implementation that `JsonbBuilder.create()` finds, on first use: xref:champollion::index.adoc[Champollion] in Vidocq. `cassini-core` depends on the JSON-P and JSON-B APIs only.

The binding itself is static: `champollion-codegen-apt` emits a `<Type>$$Binding` at compile time for each `@JsonbStatic` record and for the types the application's resources exchange (xref:champollion::reference.adoc#rest-bindings[REST bindings]). No runtime reflection, no on-the-fly `setAccessible`. A type without a binding keeps the reflective JSON-B mapping.

== Vauban integration (CDI)

[source,java]
----
// SPI in cassini-api (io.vidocq.cassini.spi.bean):
public interface BeanProvider {
    interface Factory {
        BeanProvider create();
        default int priority() { return 0; }
    }
    Set<Class<?>> getResourceClasses();
    <T> T getBean(Class<T> type);
    default Object contextualInstance(Class<?> type, Object bean) { ... }
}
----

`cassini-cdi-vauban` provides `VaubanBeanProviderFactory` via `module-info.java`:

[source,java]
----
provides io.vidocq.cassini.spi.bean.BeanProvider.Factory
    with io.vidocq.cassini.cdi.vauban.VaubanBeanProviderFactory;
----

Cassini discovers Vauban via `ServiceLoader`, walks the `BeanManager` at stack construction, and stores `@Path` / `@Provider` classes. For every dispatch, `getBean()` calls `container.select(type)` — the CDI scope (`@RequestScoped`, `@ApplicationScoped`, ...) is honoured. `contextualInstance(...)` unwraps the client proxy of a normal-scoped bean to the real contextual instance, so `@Context` field injection lands on the object the method body actually executes on (invocation still goes through the proxy).

The `CassiniScopeExtension` (Vauban Build Compatible Extension) adds `@RequestScoped` to `@Path` classes lacking an explicit scope — automatic alignment with the semantics filters and interceptors expect. Interfaces, such as MicroProfile Rest Client contracts, keep no scope.

=== The request scope ends with the request

`CdiRequestScopeFilter` (`cassini-cdi`) and `VaubanRequestScopeFilter` (`cassini-cdi-vauban`) activate the request scope in a pre-matching request filter that runs before every other filter. They do not end it in a response filter, which runs before the entity is written and not on every path. They hand the request an end-of-request action instead, as the `io.vidocq.cassini.requestCompleted` property (a `Runnable`), and `DefaultCassiniHttpAdapter.dispatch` runs it in a `finally`, once the dispatch is over, on the thread that ran the filters. So:

* a `MessageBodyWriter`, a `WriterInterceptor` or a `StreamingOutput` still sees the scope and the `@RequestScoped` beans;
* the scope ends exactly once on every path: a match, a 404 or 405, a mapped or unmapped failure (500), a failed write, and an async response resumed from another thread (the dispatch thread waits for it);
* a scope that is already active on the thread is not the filter's: under the Vidocq runtime, whose hook (`RequestContext#runInScope`) opens and ends the scope itself, the Vauban filter does nothing; on an application server `RequestContextController#activate` answers `false` and nothing is ended.

The scope of a streamed SSE response ends with the resource method that opened the sink, not with the last event. The properties of a request are one store, an exchange attribute built by the first property set (a request allocates nothing for it before) and shared by the request and response contexts of the filters and by the reader and writer interceptor contexts.

== JAX-RS Client (`cassini-client`)

`cassini-client` is a standalone implementation of the Jakarta REST 4.0 **Client API** with no external dependency: it builds on the JDK `java.net.http.HttpClient` running on virtual threads. It exposes no public package — the whole surface is consumed through `jakarta.ws.rs.client.*` and discovered via `ServiceLoader`:

* `provides jakarta.ws.rs.client.ClientBuilder with CassiniClientBuilder` — `ClientBuilder.newClient()` returns a Cassini client whenever `cassini-client` is on the path.
* `provides jakarta.ws.rs.ext.RuntimeDelegate with CassiniClientRuntimeDelegate` — makes the module self-contained for `UriBuilder.fromUri(...)`; all transports point to the same `CassiniRuntimeDelegate`, so there is no runtime divergence when several are present.
* `uses jakarta.ws.rs.core.Feature` — third-party `Feature`s (MicroProfile Telemetry instrumentation, auth, logging…) registered via `ServiceLoader` are auto-applied by `CassiniClientBuilder.build()` on a `FeatureContext` adapter.

It reuses `MessageBodyRegistry`, `CassiniResponse`, `CassiniUriBuilder` and `CassiniRuntimeDelegate` from `cassini-core` — request/response (de)serialization is shared with the server side. `ClientRequestFilter` / `ClientResponseFilter` are `@Priority`-ordered; `AsyncContextPropagator` carries the async invocation onto a virtual thread.

== Virtual threads and async

* All blocking I/O (body read, backend wait, SSE) runs on a virtual thread created by `Executors.newVirtualThreadPerTaskExecutor()`.
*On Chappe, when a request scope hook (`ChappeHttpAdapter.Scoped`, which the Vidocq runtime installs) bounds the request scope by the dispatch, a request is dispatched on the virtual thread of its connection, unless the deployment may stream: a resource method with an `SseEventSink`, or a sub-resource locator resolved at run time (`CassiniHttpAdapter.mayStream()`). Otherwise `ChappeHttpAdapter` starts a virtual thread per request, as every request did until 0.4.0-RC1: Chappe can then send a stream while the method goes on writing events.
* `@Suspended AsyncResponse` immediately releases the carrier thread; resolution is posted by user code on a VT.
* A `CompletionStage` returned by a resource method is propagated down to the transport via `CassiniAsyncContext`.

Real-time chunked SSE streaming shipped with **M2i** (lazy-commit latch + thread-agnostic chunk queue in `ChappeHttpAdapter` — see `ASYNC.md`). **M2h** (true non-blocking `CompletionStage` propagation to the transport) was dropped as a non-goal: blocking on a virtual thread already yields the carrier, so it buys nothing measurable on JDK 25. See xref:tck.adoc[TCK status].
